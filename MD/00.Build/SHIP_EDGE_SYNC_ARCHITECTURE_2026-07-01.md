## 1. 요구사항 원문 및 재정의

### 1.1 사용자 요구 (원문)
1. 일반적인 접속 — 현재 `pms` / `ycpms` 처럼 사이트에 바로 접근
2. 선상은 인터넷이 불안정하므로 **인트라넷으로 서버 및 프론트를 자체 운영**
3. 선상 서버가 **일정 간격으로, 인터넷이 좋을 때** 중앙 서버로 정보 전달
4. 선상 서버는 **계속 추가**됨

### 1.2 요구사항 재정의 (검증된 형태)

| # | 유형 | 요구사항 | 수용 기준(AC) |
|---|------|----------|----------------|
| FR-1 | 기능 | 육상(사무실) 사용자는 클라우드 중앙 사이트에 브라우저로 직접 접속한다 | `pms.toads.kr` / `ycpms.toads.kr` 형태 유지, 전 선박 데이터 조회 |
| FR-2 | 기능 | 선박 승조원은 **인터넷 없이도** 선내 LAN으로 PMS 프론트+API+DB를 사용한다 | 위성/LTE 끊긴 상태에서 정비 등록·조회·재고 처리 100% 동작 |
| FR-3 | 기능 | 선박 노드는 **인터넷 회선을 감지하면 즉시** 중앙과 양방향 동기화한다 (고정 주기 아님) | 회선 복구 감지 후 수 초~수십 초 내 자동 동기화 개시, 오프라인 중 누적분 무손실 반영 |
| FR-4 | 기능 | 선박 노드를 **무중단으로 계속 추가**한다 (회사당 20~30척 규모, 설치는 자체 수행) | 신규 선박 온보딩이 내부 표준 절차/스크립트로 반복 가능, 중앙 코드 변경 불필요 |
| FR-5 | 기능 | 한쪽에서의 **삭제가 반대편에도 전파**된다 | 선박/중앙 어느 쪽 삭제든 동기화 후 상대에도 반영 (유령 레코드 없음) |
| FR-6 | 기능 | 선박 승조원은 **오프라인에서 로컬 DB로 로그인**한다 | 중앙→선박으로 `user`(자격 사본) 하향 동기화되어 회선 없이 인증 성공 |
| NFR-1 | 신뢰성 | 오프라인 중 생성 데이터는 유실·중복 없이 정확히 1회 반영된다 | 재시도/중단/재접속 시에도 멱등(idempotent) |
| NFR-2 | 보안 | 선박↔중앙 동기화 채널은 인증·암호화된다 | 노드별 자격증명, TLS, 미인증 요청 거부 |
| NFR-3 | 일관성 | 양쪽에서 수정된 레코드의 충돌은 **정의된 규칙**으로 해소된다 | 필드/레코드별 소유권(authority) 규칙 문서화 및 구현 |
| NFR-4 | 운영성 | 각 선박 노드의 동기화 상태를 중앙에서 관측할 수 있다 | 마지막 동기화 시각·지연·실패를 대시보드/로그로 확인 |

## 2. As-Is 아키텍처 분석 (현재 코드 기준)

> **핵심 발견: 동기화의 골격(scaffold)이 이미 구현되어 있다.** 본 요구는 "신규 구축"이 아니라 "기존 골격의 완성·강건화·확장"이다.

### 2.1 이미 존재하는 것 ✅

| 구성요소 | 위치 | 현황 |
|----------|------|------|

| 다운로드(중앙→선박) | `app/api/scheduler/receive/route.ts` | 로컬 `max(last_receive_date)` → `POST {REMOTE}/api/data/all/get` → MERGE |

## 3. To-Be 아키텍처 (토폴로지)

```
                         ┌──────────────────────────────────────┐
   육상 사용자(브라우저) ─▶│         중앙 클라우드 (AWS)          │
   pms.toads.kr           │  ALB → ECS(Next.js) → RDS(Postgres)  │◀── 전 선박 집계 뷰
   ycpms.toads.kr         │   /api/data/*  (동기화 수신 게이트웨이)│
                         └──────────────▲───────────────────────┘
                                        │  HTTPS + 노드 토큰 (선박이 능동 발신)
                    ┌───────────────────┼───────────────────┐
                    │                   │                   │
        ┌───────────┴──────┐ ┌──────────┴───────┐ ┌─────────┴────────┐
        │  선박 A 엣지노드  │ │  선박 B 엣지노드 │ │  선박 N …(증설)  │
        │ Next.js+Postgres │ │ Next.js+Postgres │ │  동일 이미지     │
        │  선내 LAN 전용   │ │  선내 LAN 전용   │ │                  │
        │  승조원 브라우저  │ │  승조원 브라우저 │ │                  │
        └──────────────────┘ └──────────────────┘ └──────────────────┘
        (인터넷 없어도 100% 동작, 회선 복구 시 능동 동기화)
```

### 3.1 핵심 설계 원칙
1. **선박 능동 발신(ship-initiated) 고정.** 선박은 공인 IP·인바운드가 없으므로 **중앙이 선박에 접속하지 않는다.** 업로드/다운로드 모두 선박이 outbound로 개시. (현재 코드가 이미 이 방향 — 유지)
2. **오프라인 우선(offline-first).** 엣지 노드는 자체 Postgres로 완결 동작. 중앙은 "최종 진실의 집계본"이지 실시간 의존 대상이 아님.
3. **동일 코드베이스·동일 이미지.** 엣지/중앙은 같은 Next.js 이미지. 역할은 환경변수(`NODE_ROLE=edge|central` 등)로 분기. (배포·유지보수 단일화)
4. **선박 단위 파티셔닝을 소유권으로 승격.** `vessel_no`로 물리 분리된 현 구조를 "레코드 소유권" 규칙으로 공식화하여 충돌을 구조적으로 제거.

### 3.2 데이터 소유권(authority) 모델 — 충돌 해소의 근간
LWW(나중 승리)는 위험하다. 레코드/필드별 **단일 소유자**를 정의해 충돌을 원천 차단한다.

| 데이터 | 생성/수정 주체 | 동기화 방향 | 충돌 규칙 |
|--------|----------------|-------------|-----------|
| 정비 실적(`maintenance_work`), 부품사용(`used_parts`), 입·출고·손실(`receive`/`release`/`loss`), 운전시간 | **선박(엣지)** | 선박 → 중앙 (upload 전용) | 선박이 소유자. 중앙은 읽기전용 사본 |
| 장비/섹션/자재 마스터(`equipment`/`section`/`material`), 정비계획(`maintenance_plan`) | 원칙적으로 **육상(중앙)** 정의 | 중앙 → 선박 (download) | 중앙이 소유자. 선박은 사본 |
| 정비 연장 **승인**(`maintenance_extension.approval_*`) | 신청=선박 / **승인=육상** | 양방향 (필드 분리) | 신청필드=선박 소유, 승인필드=중앙 소유 |
| 사용자·권한(`user`) | 육상(중앙) | 중앙 → 선박 (오프라인 로그인용 하향) | 중앙이 소유자 |

> **결론(결정 반영):** 선박은 마스터(장비/계획/자재)를 **편집하지 않는다(§9-Q5 확정)**. 따라서 마스터는 중앙→선박 단방향 사본이며, 진짜 양방향 충돌은 `maintenance_extension`(신청↔승인) 1건에 국한된다. **필드 단위 소유권**으로 해소 가능 → 복잡한 CRDT/버전벡터 불필요.

### 3.3 삭제 동기화 설계 (FR-5, GAP-11)
현 MERGE는 UPSERT만 하므로 삭제가 전파되지 않는다. **소프트 삭제(tombstone)** 방식을 권고한다 (물리 DELETE 지양 — 물리 삭제는 "사라진 행"이라 델타 추적 자체가 불가).
- 전 업무 테이블에 `deleted_yn`(또는 `deleted_at`) 컬럼 추가. 삭제 = 플래그 세팅 + `modify_date` 갱신 → 기존 델타 파이프라인에 자연 편승.
- 수신측 MERGE는 `deleted_yn='Y'`면 상대 사본도 소프트 삭제 반영.
- 조회 쿼리는 `deleted_yn='N'` 필터 일괄 적용(전 read 경로 점검 필요 — 작업량 있음).
- 소유권 규칙 준수: 삭제도 **소유자만** 가능(선박 소유 실적은 선박만 삭제, 마스터는 중앙만 삭제).

### 3.4 동기화 트리거 = 회선 감지 즉시 (FR-3)
고정 주기 cron이 아니라 **연결 감지 기반**으로 설계한다.
- 엣지 노드에 경량 연결 감시자: 중앙 `/api/health`로의 도달성을 짧은 타임아웃으로 폴링(예: 15~30초) → **끊김→복구 전이(edge transition)를 감지한 순간 즉시** send→receive 실행.
- 동기화 중 재끊김 대비: 실행은 지수 백오프 재시도, 동시 실행 방지 락(중복 트리거 무시).
- "즉시"의 하한: 감지 폴링 간격이 실질 지연(수 초~수십 초). 상시 폴링 부담은 미미.

## 4. 심층 검증 — 계획(Plan) 관점

### 4.1 접근 전략: 신규 구축 ❌ → 골격 완성 ✅
기존 `scheduler`·`data` 골격과 델타 컬럼이 있으므로, "동기화 엔진을 새로 만드는" 프로젝트가 아니라 **"미완 골격을 완성하고 보안·운영을 입히는"** 프로젝트로 규모를 재산정한다. 이는 일정·리스크를 크게 낮춘다.

### 4.2 리스크 등급표

| 리스크 | 심각도 | 발생가능성 | 완화책 |
|--------|--------|-----------|--------|
| 동기화 채널 무인증 노출(GAP-3/4) | **높음** | 확실(현재 상태) | 노드 토큰 + mTLS/Allowlist, 게이트웨이 인증 미들웨어 |
| receive 편측 유실(GAP-2) | 높음 | 확실 | 누락 테이블 MERGE 보강 + 커버리지 테스트 |
| 오프라인 채번 충돌(GAP-9) | 중간 | 조건부 | 소유권 모델로 방향 고정(선박만 채번) + 노드 프리픽스 |
| 시계 오차 델타 오판(GAP-8) | 중간 | 조건부 | 서버 `now()` 단일 기준 + 단조 증가 시퀀스/워터마크 |
| 엣지 HW 장애·데이터 손실 | 높음 | 조건부 | 엣지 로컬 백업 + 중앙이 사실상 원격 백업 역할 |
| 선박 HW/설치 운영부담(FR-4) | 중간 | 확실 | 표준 이미지·부트스트랩 스크립트·온보딩 체크리스트 |

### 4.3 단계별 로드맵 (권고)

## 5. 심층 검증 — 설계(Design) 관점

### 5.1 엣지 노드 물리 구성
- **하드웨어:** 산업용 미니PC/NUC급(팬리스 권장), UPS, 선내 LAN 스위치 연결. 위성/LTE 라우터는 **선택적 outbound**로만 사용.
- **소프트웨어:** Docker Compose 1벌 = `web`(Next.js standalone) + `db`(Postgres 15) + `sync`(cron). 완전 자기완결.
- **접속:** 승조원은 선내 LAN에서 `http://ship-pms.local` 또는 고정 사설IP로 접속. 인터넷 불요.

### 5.2 동기화 프로토콜 (강건화 설계)
현재 "전부 조회 → 통짜 POST" 방식을 다음으로 보강:

1. **워터마크 기반 델타:** 노드별 `sync_state(vessel_no, table, last_ack_watermark)` 테이블 도입. `modify_date` 시계 대신 **중앙이 발급/확정한 워터마크**를 기준점으로 사용 → GAP-8 완화.
2. **멱등 수신:** 모든 `/api/data/*`를 자연키(PK) 기준 MERGE로 유지(현재 방식 OK) + `sync_batch_id` 헤더로 재전송 중복 무시.
3. **원자적 확정(2-phase):** 선박은 (a) 업로드 → (b) 중앙 `ack` 수신 후에만 `last_send_date` 커밋. 현재 코드는 이 순서(응답 ok 후 update) — **유지**. 단, 부분 실패 대비 배치를 트랜잭션·재시도로 감쌀 것.
4. **재시도/백오프:** 회선 불안정 전제 → 지수 백오프 + 지터, 실패 배치 보존.
5. **연결 타임아웃 필수:** `connectionTimeoutMillis`·`statement_timeout` 설정(GAP-7). 선상에서 무한 대기 금지.

### 5.3 보안 설계 (NFR-2)
- **노드 신원:** 선박 노드마다 발급된 **장기 토큰(또는 클라이언트 인증서)**. `Authorization: Bearer <node-token>` 필수.
- **게이트웨이 인증 미들웨어:** `/api/data/*`·`/api/scheduler/*` 진입점에서 토큰 검증 + `token→허용 vessel_no` 매핑 강제. 토큰이 소유하지 않은 `vessel_no` 페이로드는 거부. (GAP-3/6 동시 해결)
- **전송 보안:** 중앙은 HTTPS 고정. 가능 시 중앙 앞단에 IP allowlist/WAF.
- **비밀 관리:** 노드 토큰·DB 자격증명은 이미지에 굽지 않고 노드 로컬 시크릿으로 주입(현 Secrets Manager 관행의 엣지판).

### 5.4 데이터 일관성·충돌 (NFR-3)
- §3.2 소유권 모델을 **코드로 강제**: 수신 MERGE 시 "소유자가 아닌 필드는 갱신 금지". 예) 중앙이 선박 소유 필드(정비 실적)를 수정해 내려보내지 않음, 선박이 중앙 소유 필드(승인상태)를 덮어쓰지 않음.
- `maintenance_extension`만 필드 분리 MERGE(신청필드/승인필드 각각의 소스만 반영).
- **삭제 동기화 정책 필요(현재 부재):** 물리 삭제 대신 `use_yn`/soft-delete 확인 후 tombstone 전파 방식 권장. (§9 결정 필요)

### 5.5 신규 선박 온보딩 설계 (FR-4)
표준 절차화:
1. 중앙에 `vessel` 마스터 + 노드 토큰 발급(관리 UI/스크립트).
2. 엣지 이미지 배포 + `.env`(VESSEL, REMOTE_SITE_URL, NODE_TOKEN) 주입.
3. 최초 부트스트랩: 중앙 → 엣지로 마스터/계획/사용자 **초기 풀 동기화**.
4. 헬스체크 후 운영 개시. **중앙 코드 변경 없이** N회 반복 가능해야 함(멀티테넌시가 데이터 기반이어야 하는 이유).

### 6.2 기존 자산 재사용 포인트
- `adaptNamedParams`(@name→$N), `withTransaction`, 델타 쿼리 패턴, MERGE UPSERT 관용구는 그대로 재사용 → 신규 코드량 최소화.
- 멀티배포(`APP_ENV`) 파이프라인을 엣지 이미지 빌드에 재활용.

### 6.3 테스트 전략 (quality)
- **오프라인 시나리오:** 회선 차단 상태 CRUD → 복구 → 무손실/무중복 반영 검증(멱등).
- **양방향 충돌:** `maintenance_extension` 신청/승인 동시 편집 케이스.
- **커버리지 회귀:** send가 내보내는 테이블 집합 == receive/set이 반영하는 집합 (GAP-2 재발 방지 단위테스트).
- **보안:** 무토큰/타 vessel 토큰 요청 거부.
- **부하:** N척 동시 동기화 시 중앙 RDS 커넥션 풀·락 경합.

## 9. 결론 및 다음 단계

- 본 요구는 **신규 구축이 아니라 기존 동기화 골격(`scheduler`/`data` + 델타 컬럼)의 완성·보안·확장 프로젝트**이다. 이 재프레이밍이 일정·리스크를 크게 낮춘다.
- **가장 시급한 것은 기능이 아니라 보안(GAP-3/4)과 안정성(GAP-7)** 이다. 현재 동기화 엔드포인트를 그대로 인터넷에 노출하면 임의 데이터 주입이 가능하다. P0로 최우선 처리.
- 충돌은 **소유권 모델(§3.2)로 구조적으로 제거** 가능하여, 무거운 분산 동기화 기법(CRDT/버전벡터)은 불필요하다.
- 확장(FR-4)은 **"데이터 기반 멀티테넌시 + 노드 토큰 등록 체계"** 가 성립해야 중앙 코드 변경 없이 반복 가능하다(현재 `VESSEL` 하드코딩·`APP_ENV` 다중배포로는 척수 확장에 부적합).
